# Assumptions and decisions

This log records ambiguities and decisions for the fictional Kaveri Home Goods scenario. No real merchant interview or customer data is represented.

| ID | Ambiguity | Decision | How to validate / change |
|---|---|---|---|
| A1 | What stock number means sellable | Use an explicit global `actual_available_stock`, or the documented per-location actual-availability field only when there is exactly one location. If neither is available or several locations require an allocation rule, return `unknown`; never substitute physical stock. | Ask the merchant how committed orders, reservations, locations and channel allocation affect fulfillment; compare the selected field with their order allocation workflow. |
| A2 | Missing reorder level | Use `DEFAULT_LOW_STOCK_THRESHOLD` (default 5) only when the verified stock field exists; include the threshold logic in tool documentation. | Ask for SKU-level replenishment rules and category exceptions. |
| A3 | Razorpay-to-Zoho order matching | `razorpay_order_id` is searchable only when a merchant stores it in Zoho's `reference_number` or a configured custom field. Always return `match_basis`; never fuzzy-match silently. | Inspect a throwaway org's schema and ask which identifier is copied during order creation. |
| A4 | Missing package, tracking or delivery data | Mark fields `not_available`; do not infer shipment or delivery from order status. | Compare a sample of the merchant's delivered orders to Zoho records and identify the source of truth. |
| A5 | Quota values | Use configurable defaults from the PRD. Current actual plan limits remain unverified until cited in `API_NOTES.md`; surface observed code 45 without retry. | Check the account's plan and current Zoho docs; ask what other integrations share the organization quota. |
| A6 | OAuth writes versus read-only connector | OAuth authorization-code exchange and refresh require HTTP POST to Zoho Accounts. “GET-only” means all Inventory data operations in `src/` are GET; no Inventory writes are exposed. The isolated trial seeder is the only code allowed Inventory write scopes. | Keep method-level tests scoped to the Inventory API client and separately assert OAuth POST targets only the Accounts token endpoint. |
| A7 | Conflicting optional-demo text | Follow AGENTS.md v2: optional M11 uses Google Gen AI/Gemini, not the older Claude wording in the run sheet's inherited plan. Defer until M1–M10 gates pass. | Verify the current Google SDK docs before implementation. |
| A8 | Evidence of live readiness | Code and docs may describe how to run live smoke, but live verification remains “not yet verified” until the author confirms a real run. | Author runs `make live-smoke` against a throwaway Zoho org and supplies the confirmation and screenshots. |
| A9 | Scope and milestone labels differ in the old tracked plan | Replace the previous M1–M9/optional-Claude roadmap with current AGENTS.md M1–M10 and optional Gemini M11. | Keep `docs/PLAN.md` as the current source of milestone status. |
| A10 | Merchant scenario facts | Kaveri Home Goods, its workflow, and all generated events are fictional hypotheses. No quote, interview, uplift, or operational baseline is claimed. | Validate the hypotheses through the discovery questions before using the design for a real merchant. |
| A11 | Agent Studio private connector integration | Public material verifies the Agent Studio product, launch agents, Claude Agent SDK, and named cart-agent build partners. How a private MCP connector is registered, how tool calls are routed, and how per-merchant credentials are stored are not established by the reviewed public sources. This repo demonstrates MCP compatibility only. | Confirm the actual integration contract with an authorized Razorpay Agent Studio owner before production integration; do not infer internal APIs from the public launch description. |
| A12 | Public pricing/discrimination discussion | Public reporting raised a question about whether personalized offers could create price-discrimination or dark-pattern risks; it did not establish that an Agent Studio agent used aggressive or discriminatory discounts. Razorpay's published response says offers are bounded by merchant-configured coupon rules. The connector supplies stock facts and does not select or send offers. | Treat this as design context, not a claim about observed agent behavior. Re-check merchant-approved offer policy before any future integration. |
