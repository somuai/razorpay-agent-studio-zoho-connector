# Architecture & Domain Assumptions

**Document:** `docs/ASSUMPTIONS.md`  
**Purpose:** Every ambiguity encountered during the design and implementation of the Zoho Inventory Connector, along with the operational decision taken and its rationale.

---

| # | Ambiguity / Decision Point | Assumption & Decision Taken | Rationale & Alternatives Considered |
|---|---|---|---|
| **A1** | **Sellable Stock Metric** | We treat `actual_available_stock` as the true sellable quantity. If absent or null from the payload, fallback to `available_stock`, then `stock_on_hand`. | In Zoho Inventory, `stock_on_hand` reflects warehouse physical presence but ignores units committed to existing orders. Nudging carts for items with physical stock that are already sold leads to unfulfillable orders. |
| **A2** | **Default Low Stock Threshold** | If an item's `reorder_level` is not configured (null or 0), the threshold defaults to `5` units (configurable via `DEFAULT_LOW_STOCK_THRESHOLD`). | Zoho allows creating items without a reorder level. Without a default, items would oscillate directly from in-stock to out-of-stock, defeating the scarcity-nudge strategy. |
| **A3** | **Razorpay Order ID Matching** | In `search_sales_orders`, the connector first matches against `reference_number`, then checks custom fields (e.g., `cf_razorpay_order_id`). The response returns `match_basis`. | Zoho Inventory does not have an out-of-the-box Razorpay integration field. Merchants typically configure Checkout to inject the Razorpay order ID (`order_xxx`) or payment ID (`pay_xxx`) into the sales order `reference_number`. Surfacing `match_basis` prevents the LLM agent from hallucinating how the link was established. |
| **A4** | **Tracking & Delivery Date Provenance** | Tracking numbers and courier status reside on the `shipmentorders` resource, linked to `packages`. The connector traverses `salesorders -> packages -> shipmentorders`. | A sales order status can say `fulfilled` even if carrier tracking has not yet synchronized. If any piece is missing, `get_order_fulfillment_evidence` marks that field `not_available` with `completeness: "partial"`. It never guesses or interpolates delivery dates. |
| **A5** | **Daily Quota Ceiling** | Daily quota defaults to 1,000 calls/day (Zoho Free tier), with configurable override via `ZOHO_DAILY_QUOTA_LIMIT`. | The connector must protect merchants on the free tier from being locked out. Quota tracking provides proactive alerts before hitting code 45. |
| **A6** | **Zero-Retry on Error Code 45** | Upon receiving Zoho Error Code 45 (daily quota exceeded), the client immediately raises `QuotaExhaustedError` and aborts retries. | Code 45 indicates a hard daily quota cutoff that only resets at 00:00 UTC / IST. Exponential backoff or retrying wastes CPU and produces misleading errors. |
| **A7** | **Strict GET-Only Surface** | No HTTP method other than `GET` is supported by the client, services, or MCP tools. | Eliminates the possibility of accidental write operations (stock adjustments, invoice edits, cancellations) caused by LLM tool hallucination. Read-only by construction. |
| **A8** | **PII Redaction Policy** | Customer phone numbers, full email addresses, and shipping street addresses are masked in default responses. Phone numbers show only last 4 digits; emails show first character and domain. Opt-in via `include_pii=true`. | Minimizes merchant data leakage into LLM inference context windows, ensuring compliance with data privacy standards and Razorpay security guidelines. |
| **A9** | **Output Truncation Cap** | Response payloads are bounded to 8 KB (8192 bytes). If a response exceeds 8 KB, it is truncated with `truncated: true` and actionable instructions to refine the query. | LLM agent context windows and token budgets are finite. Dumping large order books or full inventory tables degrades reasoning and inflates inference costs. |
| **A10** | **OAuth Loopback vs Headless** | Two auth flows supported: interactive loopback on `http://localhost:8080/callback` (FR-1.1) and headless direct refresh token via `ZOHO_REFRESH_TOKEN` (FR-1.2, Zoho Self-Client). | Headless mode is essential for CI/CD pipelines, containerized deployments, and automated testing, while loopback serves local merchant setup. |
